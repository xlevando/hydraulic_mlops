# Исследование механизмов Backpressure и Load Shedding

**Архитектура:** Клиент → FastAPI (`POST /api/v1/tasks`) → Очередь RabbitMQ (`x-max-length=100`) → FastStream Worker (4 потока, MLflow `@champion`) → PostgreSQL.
**Параметры:** 300 запросов, длительность инференса 1.0 с, `prefetch_count=4`.

## Сводная таблица результатов

| # | Режим | Accepted | Rejected (503) | Lost | Total Time | Throughput | Latency p50 | Latency p95 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 1 | **Load Shedding** | 104 | 196 | 0 | 32.3 с | 3.2 /с | 15.9 с | 29.0 с |
| 2 | **Backpressure** (1 воркер) | 300 | 0 | 0 | 88.1 с | 3.4 /с | 28.4 с | 30.4 с |
| 3 | **No Backpressure** | 300 | 0 | 0 | 89.3 с | 3.4 /с | 44.3 с | 81.4 с |
| 4 | **Backpressure** (2 воркера) | 300 | 0 | 0 | **59.9 с** | **5.0 /с** | **19.2 с** | **21.5 с** |

*(Total Time — это `elapsed_total_s`, время от старта публикации до записи последней задачи в БД).*

### Команды запуска
1. `MODE=load N_REQUESTS=300 QUEUE_MAX_LENGTH=100 uv run python -m scripts.experiment`
2. `MODE=backpressure N_REQUESTS=300 QUEUE_MAX_LENGTH=100 uv run python -m scripts.experiment`
3. `MODE=no_backpressure N_REQUESTS=300 QUEUE_MAX_LENGTH=100000 uv run python -m scripts.experiment`
4. `MODE=backpressure N_REQUESTS=300 QUEUE_MAX_LENGTH=100 uv run python -m scripts.experiment` (запущено с двумя контейнерами воркеров)

---

### 1. Load Shedding (граница системы)
**Суть:** Внешний клиент не замедлить. При переполнении API отвечает 503 с `Retry-After`.
**Результат:** Принято 104 задачи (влезли в лимит 100 + префетч 4). Остальные 196 запросов мгновенно получили 503. Все принятые задачи дошли до БД (`lost=0`). Система отработала за 32.3 с.

### 2. Backpressure (1 воркер)
**Суть:** Скрипт упирается в `reject-publish` и ждет `Retry-After` (замедляется).
**Результат:** Все 300 задач приняты и обработаны (`lost=0`). Время публикации растянулось на 60 секунд (источник подстроился под скорость воркера). Общее время выполнения — 88.1 с.

### 3. No Backpressure (демонстрация проблемы)
**Суть:** Очередь без лимита (`x-max-length=100000`).
**Результат:** Скрипт «выстрелил» все 300 задач за 3.4 секунды. Но задачи застряли в очереди: **latency p95 выросло до 81.4 с** (против 30.4 с с backpressure). Клиент думает, что всё ок, но результат ждет в 2.5 раза дольше.

### 4. Масштабирование (2 воркера)
**Суть:** Добавление второго воркера (4 потока + 4 потока) без изменения кода.
**Результат:** Пропускная способность (throughput) выросла с 3.4 до 5.0 задач/с, а latency p95 упала с 30.4 до 21.5 с. Общее время обработки 300 задач сократилось со 88.1 до **59.9 секунд**.

---

### Главные выводы
1. **Без backpressure** система накапливает сообщения в памяти брокера. Время ожидания растет нелинейно (p95 до 81 с), хотя клиент получает 202 мгновенно.
2. **С backpressure** скорость источника автоматически подстраивается под воркер (публикация занимает 60 с вместо 3 с), время ожидания предсказуемо (p95 ~30 с), задачи не теряются.
3. **Масштабирование воркеров** линейно увеличивает пропускную способность (throughput 5.0/с) и снижает общее время обработки пачки задач (59.9 с).
